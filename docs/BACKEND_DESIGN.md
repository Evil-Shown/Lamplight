# Library+ Firebase Backend Design

## 1. Firebase services

- Authentication: Google provider; optional institution SSO later.
- Cloud Firestore: catalogue projection, seats, reservations, waitlists, notifications, policy/config, audit references.
- Cloud Functions (TypeScript): all privileged/conflict-sensitive mutations.
- Cloud Messaging: push delivery.
- App Check: Play Integrity on Android, App Attest/DeviceCheck on Apple, reCAPTCHA Enterprise for web as applicable.
- Storage: approved cover assets or exported reports only; not required for core booking.
- Analytics, Crashlytics, Performance, Remote Config.
- Emulator Suite for local and CI testing.

Use separate dev, staging, and production Firebase projects.

## 2. Authentication and roles

### Google authentication

Use FlutterFire configuration generated by FlutterFire CLI. On native platforms, use official Google Sign-In and exchange the Google ID token for Firebase credentials. Configure Android SHA fingerprints and iOS URL schemes.

### Profile bootstrap

`bootstrapUserProfile`:

1. Requires Auth + App Check.
2. Validates allowed institution domain if enabled.
3. Creates `/users/{uid}` with safe default role `student`.
4. Updates non-authoritative display fields and `lastLoginAt`.
5. Returns role/profile completion state.

### Staff/admin roles

- Store role in Firebase Auth custom claims for rule checks.
- Optionally mirror role in user document for display, but claims are authoritative.
- Only Admin SDK tooling can assign roles.
- Force token refresh after a role change.
- Record role grants/revocations in audit logs.

## 3. Trusted API surface

Callable functions accept versioned payloads and return typed error codes.

### Reservation functions

- `createBookReservation(bookId, idempotencyKey)`
- `cancelBookReservation(reservationId, reason, idempotencyKey)`
- `createSeatReservation(seatId, startsAt, endsAt, idempotencyKey)`
- `cancelSeatReservation(reservationId, reason, idempotencyKey)`
- `checkInSeat(qrToken, scannerContext)`
- `checkOutSeat(reservationId)`
- `completeBookPickup(qrToken, scannerContext)`

Each validates ownership/role, policy, resource state, time, conflicts, and limits in a transaction.

### Waitlist functions

- `joinWaitlist(resourceType, resourceId, preferences, idempotencyKey)`
- `leaveWaitlist(entryId)`
- `claimWaitlistOffer(offerId, idempotencyKey)`
- `declineWaitlistOffer(offerId)`

### Staff functions

- `verifyQrToken(token, locationId)`
- `staffOverrideReservation(reservationId, action, reason)`
- `lookupReservation(reference)`

Staff actions require custom claims and create immutable audit events.

## 4. Reservation consistency

### Book allocation

Transaction:

1. Read book inventory/copy allocation summary.
2. Ensure user has no duplicate active reservation and is under limits.
3. Select or reserve one available copy.
4. Create reservation with server timestamps and pickup deadline.
5. Update availability projection.
6. Create notification/event.

### Seat conflict prevention

Use deterministic slot documents or a transactionally checked occupancy structure. For fixed slot lengths, a document such as `/seatSlots/{seatId_utcSlot}` offers simple uniqueness. For arbitrary ranges, query overlap and lock a bounded set of slot documents in one transaction.

Never trust client-provided “available” state.

## 5. Time-based workflows

Use Cloud Scheduler plus scheduled functions or Cloud Tasks:

- Reminders before seat start and book pickup expiry.
- Seat check-in grace deadline.
- Book pickup expiry.
- Waitlist offer expiry and next promotion.
- Stale device-token cleanup.
- Daily reconciliation of derived availability/counters.

All dates are stored as Firestore timestamps in UTC. Policies include a named campus timezone for display and operating-hour calculations.

## 6. QR token design

Do not encode a reservation ID alone.

Recommended payload is a compact signed token containing:

- Version and key ID.
- Random token ID/nonce.
- Reservation ID.
- Purpose (`seat_checkin` or `book_pickup`).
- Issued-at and expiry.
- Audience/location constraints.

Verification occurs in Cloud Functions. Store a hash of one-time nonce/token ID where replay detection is required. Rotate signing keys; keep old public/verification keys for a limited overlap. QR tokens should be short-lived and refreshed by the authenticated owner.

Reject:

- Invalid signature/version/audience.
- Expired/not-yet-valid token.
- Cancelled/completed reservation.
- Wrong campus/location.
- Already consumed nonce.
- Role/location mismatch.

## 7. Notifications

### Device registration

Store per-device FCM records under the user, including platform, token, app version, locale, enabled state, and timestamps. Tokens are sensitive operational data and are not readable by other users.

### Delivery

Trusted functions create a notification record and send FCM. Payload contains a notification type and entity ID, not personal details or secrets. Delivery failures update token health. Email/SMS adapters can be added behind the same notification service.

### Preferences

Respect push/email/SMS settings, reminder types, waitlist updates, quiet hours, and mandatory operational/security exceptions.

## 8. Search

Firestore supports structured filters and limited prefix patterns but is not full-text search. Start with normalised fields and carefully bounded prefix queries for the assignment scope. If production catalogue scale or typo tolerance requires more, synchronise public book documents to Algolia or Typesense through trusted functions.

## 9. Security Rules strategy

- Deny by default.
- Users can read/update only approved fields in their own profile.
- Authenticated users may read catalogue and seat definitions.
- Users read only their own reservations, waitlists, notifications, and devices.
- Reservation creation/status changes happen only through Admin SDK functions.
- Staff reads/actions require staff/admin claims.
- Audit logs are never client-writable.
- Validate field types, allowed keys, and immutable fields.

Rules and indexes are source-controlled and tested in Emulator Suite.

## 10. Abuse and cost controls

- Enforce App Check.
- Add per-user/device rate limits to callable functions.
- Bound query page sizes and require indexes.
- Prevent repeated reservation/scanner calls using idempotency and debounce.
- Set Firebase budget alerts and monitor read/write/function/FCM usage.
- Apply retention to high-volume audit/scan telemetry after policy review.

## 11. Observability

- Structured function logs with request ID, uid hash, operation, result code, and latency.
- Never log QR tokens, student IDs, emails, or notification bodies.
- Alert on function error rate, permission denials, transaction contention, scheduler failure, QR replay, and notification failure.
- Crashlytics/Performance correlate client errors using non-sensitive operation IDs.

## 12. Deployment

- Type-check, lint, unit test, Emulator rules/functions test.
- Deploy indexes/rules before functions that depend on them.
- Use staged rollout and Remote Config feature flags.
- Keep secrets in Google Secret Manager/function secrets, never Dart source or git.
- Maintain rollback instructions and backward-compatible API payload versions.
